## Creator subscriptions, gifts and tips

Central installation only: `LIGHTEK_CREATOR_SUPPORT_ENABLED=true` opens offer setup and support checkout. `LIGHTEK_CREATOR_PAYOUTS_ENABLED=true` opens release of confirmed available principal. The central site must have a super-administrator platform operator, either its existing tenant or the explicit operator selected during platform setup. Default network fee is zero; optional `LIGHTEK_CREATOR_NETWORK_FEE_CENTS` must be 0–500. Existing commerce processing-reserve settings determine the separately quoted supporter fee.

A creator opens More → Creator earnings & support, sets a monthly price and enables support. Every free or paid creator keeps **100%** of tip, gift and subscription principal. A supporter sees principal, support fees, subtotal, renewal terms and applicable-tax notice before secure checkout. These are monthly financial-support subscriptions; this change does not add subscriber-only post/media access.

Only the signed canonical commerce checkout/invoice settlement creates a creator earning. A checkout redirect, pending order or client click cannot create a paid gift. A live gift requires the creator's currently live Studio project, matching site and public post. Public gift receipts show the supporter's profile name, disclosed before payment. Refund/dispute holds are excluded from the gift display.

The existing signed commerce webhook must include its checkout, invoice and subscription events plus `charge.refunded`, `charge.dispute.created` and `charge.dispute.closed`. Keep signature verification enabled. Do not create a second unsigned creator webhook.

Supporters can resume pending checkout from payment history and cancel monthly renewal even when payment is past due or the creator has disabled new support. A canceled checkout is not a paid subscription. An expired unpaid order is reconciled by the existing expiry job. Renewal receipts retain the original creator/principal/fee snapshot. Unusual credits, partial/multi-payment invoices or changed renewal totals require review and never manufacture principal earnings.

Before release, retrieve the actual payment source and balance transaction. Pending funds, an insufficient net charge, any refund/dispute, an unverified payout account or a changed in-flight destination block release. The transfer is exactly the full principal, bound to that charge and a stable idempotency key. A persisted `transfer_pending` intent survives a lost HTTP response; retry against the same account/key. Do not switch destinations to escape uncertainty.

`transferred` means credited to the verified payout account. It does not mean `bank_paid`. Use existing secure payout-account setup at `/dashboard/susu/payout-account`; bank details remain with the existing payment rail. Partial refunds/disputes hold the earning and attempt an idempotent full reversal of its own transfer; do not fund it from another creator. A failed reversal requires operator reconciliation. No automated YouTube estimate payout is introduced.

Acceptance: use two ordinary accounts. Test a tip, a live gift and a monthly subscription; inspect the signed receipt, exact principal, fee disclosure, duplicate-event handling, cancellation, failed payment, refund and account-scoped earnings. Verify a real account credit and subsequent external bank delivery separately. This work did not charge anyone or move production funds.

## Central YouTube publishing

Central infrastructure stores OAuth `client_id`, `client_secret` and `refresh_token` in Vault. Allow consumer `LightekPwa::YoutubeApi`, purpose `youtube_publishing`. Configure `LIGHTEK_YOUTUBE_CREDENTIAL_SLUG`, the exact `LIGHTEK_YOUTUBE_CHANNEL_ID`, and `LIGHTEK_YOUTUBE_UPLOADS_ENABLED=true` on the central installation only. Do not copy these credentials to a member instance. Default channel admission is 20 uploads in a rolling day and 10 per creator; `LIGHTEK_YOUTUBE_DAILY_UPLOAD_LIMIT` is configurable and must fit actual channel quota/capacity.

The author first uploads one original to their own current source application and creates a public video/clip, then chooses Publish to YouTube, confirms redistribution rights and accurately selects the children's audience. Other users cannot authorize that video. Private, restricted, community-only, reply, expired, hidden, missing-original or multiple-original submissions are rejected. Sharing an existing YouTube URL remains a separate embed action and does not establish channel ownership or attributable revenue.

Local central posts read their own original. Connected paid instances send an authenticated source identity and expiring original-only grant through the existing federation connection. Central derives the source hostname from the verified order, pins transfer to its managed server address, follows no redirects, limits bytes and checks the original checksum. Temporary central staging is purged after public processing; the member's original remains. Free member backends use the same narrow content peer protocol; their token cannot use agency resale, payment or server-administration federation endpoints.

The worker verifies the actual authorized channel, creates a resumable session and stores its sensitive session URL in Vault before sending bytes. PostgreSQL session locking spans network requests without rolling back durable receipts on a lost response. Each attempt probes the same session first. An expired/unknown session requires reconciliation; never start a replacement blindly. Find the publication UUID in the channel video's description if manual channel reconciliation is required.

An uploaded video is not playable yet. Only a provider receipt showing processed, public and embeddable activates its YouTube ID in the source PWA. Pending submissions show a processing placeholder. Legacy native videos remain compatible; not every historical video has been submitted. API/project/channel restrictions can prevent public embedding. Verify actual returned status; do not infer success from an upload request or promise ad eligibility from upload success.

Authors can request channel removal. Making the source private/hidden/restricted or deleting it queues withdrawal, retaining a durable operation after source deletion. A late upload/processing response cannot overwrite withdrawal intent. The worker deletes the known channel video and confirms deletion before `withdrawn`. An expired uncertain session requires channel review. Original retention and source-post removal are distinct operations. Operators inspect pending/reconciliation states in the revenue panel.

`CommercialRecoveryJob` runs every five minutes for bounded recovery of lost enqueues and pending settlement/uploads. Pending uploads also enqueue their next bounded continuation. Confirm scheduled jobs and queue consumers are active in production. A ready video is not evidence of channel monetization/YPP eligibility.

Acceptance: connect the actual channel, publish one owned original from each supported source path, inspect the upload receipt, public processed state and PWA playback, interrupt/recover an upload, and confirm withdrawal. Production OAuth/channel acceptance was not performed here.

After a verified active Business purchase, the member becomes their own white-label agency with an agency profile, under the existing upstream account relationship. Staff/directory roles cannot be converted through this path, and payment never grants super-administrator powers. ## Shared hosting and dedicated hosting

Free membership uses **shared hosting**: one Rails application, PostgreSQL database, Redis queue, worker and media store per free-member server. Each customer gets a User and account-scoped Site, storage allowance and sign-in connection. Account hostnames route into that same runtime; they are not separate Rails installations. Paid Personal and Business membership uses **dedicated hosting**, with a separately provisioned server/runtime and that customer's data.

1. Start with the smallest priced 1 GB-or-larger provider plan. The starter defaults to 25 shared accounts, 256 MB media per account, bounded processes/dependencies and a 2 GB swap reserve. The account limit is an operator admission control, not a measured concurrency or hardware-capacity promise. The package option checks one runtime's RAM and account storage allowances, rather than reserving a Rails/database/worker stack per user. Provider price and explicit spending budget remain checked. Nothing automatically purchases or resizes a server.
2. In PWA Administration → Memberships & YouTube revenue, select a default free-member server or round robin. Full/paused/unsafe pools are skipped; an unavailable explicit default queues signup rather than putting originals on central Lightek. Changing routing affects new placements. **Save account limit** changes admission on an existing server without a purchase or moving accounts. Dashboard notifications warn at 80% reserved or one account space remaining, and again when full. These are configured-account alerts, not CPU/RAM/disk telemetry.
3. Migration `20261118120000` preserves existing installations. Where a pool has exactly one ready, correctly owned customer runtime, it reuses that runtime in place and keeps the original pool runtime as standby. Existing post/reply IDs, media and hostname stay put. A one-slot starter becomes a 25-account starter. The SSH installer checks the standby for other users/posts/Studio projects/media before pausing its worker/dependencies and routes; its data/volumes are retained. Multiple existing customer databases are never merged by guessing: their legacy bindings remain intact.
4. New signup reserves an account and adds its logical Site to the existing pool runtime over Gatekeeper's root SSH transport. There is no per-signup Launch, cloud node, database or worker allocation. DNS/TLS/HTTPS account-identity verification must pass before ready. A retry reuses the reservation. Machine credentials stay in Vault. The one-use 90-second central sign-in ticket, account-owner checks, existing MFA lifecycle and per-account media accounting apply to the shared runtime. Generated Studio media is attributed to its project owner as well. Shared infrastructure remains under the platform operator's control.
5. A paid order must first pass the existing Dymond Bank billing path and native server delivery. Source and destination code/schema must match. `AccountSnapshot` validates its reviewed free-content graph and refuses active Studio/video work or unsupported owned tables. It installs PostgreSQL row guards for the upgrading account after draining in-flight writes; the shared database and worker remain online. A final selection under the brief DDL lock closes the preflight race. The account archive contains the selected user/profile, posts/replies, configuration, Studio graph, authorized conversation history and originals. Other contacts are suspended public identity placeholders, never copies of their credentials/private accounts. Shared sessions, Redis, installation/Vault master keys and other customers' data are excluded.
6. Check available scratch space, transfer bounded 4 MiB checksum-verified chunks, and import into an independently probed empty dedicated target held read-only with its own rollback backup. Verify row counts, foreign references and each original's bytes/checksum. Keep IDs stable, rewrap only that customer's MFA and federation token under the destination's own key, and initialize functional registries. Reapply the purchased package/Business role. Independent public HTTPS identity and package verification precedes rebinding the existing central peer/reference URLs. Historical central posts and central network interactions stay central; the central database is never copied to a customer.
7. Source customer URLs redirect to dedicated hosting. Fixed shared-host health/revision routes continue answering from the shared runtime, including when the first adopted customer upgrades. After confirmed cutover, the source account becomes read-only at the application boundary and temporary database guards are released so shared-host schema updates can continue. The immutable account archive and retained source originals are preserved; `retire_after` records seven days, but no automatic destructive cleanup is claimed. Retained rows/media continue consuming source capacity until reviewed retirement. Other shared accounts stay on shared hosting.
8. Before destination activation, Retry setup / Restore retained source preserves the previous source and can restore the unused dedicated target. After activation, rollback is refused because the dedicated instance may contain new writes; reconcile or perform a verified reverse transfer. Native code updates refuse active account migration locks. Legacy single-account runtimes keep their original transfer protocol with an explicit guard against dumping a multi-account/shared database.

Deployment still requires updating the selected shared runtime to the same release as central and the paid installer, then accepting a real separate-host signup and upgrade. Database/SSH-boundary checks are not claims of production payment, upload/playback or external mail acceptance. Full private cross-instance feeds/follows are not advertised as complete. Mail stays on its existing cluster.

## Finalized and funded view earnings

Enable `LIGHTEK_VIEW_PAYOUTS_ENABLED=true` only after funding/recipient acceptance. The owner records one completed whole-channel month in revenue administration using `date,video_id,estimated_revenue_usd,views`, one row per video/Pacific day, plus the finalized channel USD-cent amount, reference and supporting receipt. Include platform/free/deleted-video revenue in the denominator. The current importer accepts nonnegative estimates and requires positive total estimated revenue. Negative corrections and revisions to a finalized/paid month need explicit accounting review; never replace paid history.

The model scales each eligible video's daily revenue by finalized whole-channel proceeds divided by the whole-channel estimate, then applies the contractual 80% share for complete historical paid reporting days. It groups creator/video earnings and rounds each allocation down to cents; rounding remains with Lightek. Free/platform rows reduce the denominator correctly. Cancellation does not erase historical earned eligibility. The owner attests to report completeness and the finalized channel amount; this is retained documentary evidence, not an automatic AdSense API reconciliation.

After channel funds arrive, fund the outgoing platform payment balance separately and enter its top-up ID. The API verifies the actual platform top-up's succeeded/available USD balance transaction, live mode in production and coverage of all batch creator liabilities. A funding reference cannot fund a second batch. Funding fees/shortfalls are Lightek's responsibility. The platform's automatic bank payouts must be set to manual while creator liabilities are reserved; never let an automatic sweep spend the reserve.

The member sees estimates separately from finalized earnings, calculated earnings per 1,000 eligible views, funding/transfer states and payout setup/release controls. Release re-verifies the top-up, platform account and verified destination, checks all outstanding view and support-principal reserves, commits the pending destination/key before sending, verifies the provider receipt and records an account transfer. Lost-response retries search actual destination transfer history. A request older than 23 hours without a reconciled receipt blocks another create; support transfers have the same no-blind-old-retry rule. Provider reversal/unavailability holds view funding until the owner re-verifies it. A transfer is not bank-paid. Bank delivery follows the existing payout account schedule and must be accepted independently.

## Final launch acceptance

Registration must recognize the protected platform-operator binding for imported sites as well as a super-admin tenant. PWA signup creates its durable `queued` member-setup request inside the account transaction and enqueues the existing MemberSignupJob. Ordinary sites and non-PWA registration do not allocate a platform backend; editable manifest data cannot authorize this flow. An enqueue outage leaves the durable request for commercial recovery. HTTP regression coverage substitutes only host password validation/session completion, not site policy, request persistence or job payloads. Actual fresh-user production acceptance remains required.

Complete ordinary-user signup → confirmation → backend ready → first post → reply/message → return visit. Test desktop, mobile, keyboard, readable contrast and installed/offline-shell behavior. Verify real branded mail send/receive and spam controls. Publish launch programming, clips, welcome posts and two or three actively hosted communities.

Only then record a production launch decision against the deployed source revision and actual receipts. Training data preparation, local tests and a green deploy alone are insufficient.

## Installer recovery and scheduled-job dispatch

Production operations #440–442 completed dependency installation but failed while booting `db:create`: `dymond_site_patch.rb` inspected site columns before `dymond_site_sites` existed. The initializer now defers the alias until the database and table exist, then applies it on the next prepare/boot. It preserves actual domain columns and does not suppress unrelated database errors. The focused regression loads the actual initializer against an empty SQLite database, creates the schema, and verifies writes and queries through the domain alias. A missing-database fixture covers `db:create`; live PostgreSQL migration and app acceptance remain pending deployment.

The 09:00 production logs also still contain a sidekiq-cron `perform_async` dispatch error. Explicit application schedules alone have not established that all persisted or engine schedules are healthy. The provided log does not identify the failing schedule; this remains a separate internal scheduler investigation rather than the confirmed native-installation blocker above.

Production retry operation #432 reported `installer bootstrap line 82 exit 128` while cloning ruby-build. Bootstrap previously created `.rbenv/plugins` as root before cloning as the application user. It now creates or repairs that parent with the application user's ownership and mode 0755. The regression exercises real Git against an unwritable parent, then verifies clone and repeat-update recovery. Retry the same pool after deployment; live installation acceptance is still required.

All `config/schedule.yml` entries explicitly use Active Job dispatch. The pinned sidekiq-cron 1.12 adapter must call configured `perform_later`, not `perform_async` on `ActiveJob::ConfiguredJob`. The server Redis connection is configured before startup hooks. Restart workers after deployment to reload the persisted schedule definitions. The public scheduler regression executes the actual pinned cron-to-Active-Job enqueue path; its Redis history writes are the test boundary.

Native setup reserves the domain/owner/project identity atomically before host bootstrap. A stopped first bootstrap can resume its own ownership record. An older unowned directory is recoverable only when it contains an empty `releases` skeleton with empty 20-hex release directories; existing environment, storage, release files and symlinks block adoption. Known owned legacy records retain their adapter metadata. This is not permission to adopt another tenant or reset a populated instance.

Use **Retry setup on existing server** for the existing pool after a repair. It requeues the same pool/launch/request and does not request a replacement server. A ready or paused pool cannot use this retry control. The existing advisory lock prevents overlapping installer execution.

Bootstrap, starter preparation and the native installer emit a fixed `LIGHTEK_INSTALLER_FAILURE scope=... line=... exit=...` marker on command failure. The operation error retains only validated scope/line/status fields. Commands, environment values and raw output are not copied into the operation diagnostic. The first inner failure wins over outer wrapper failures; the next attempt clears old markers. Follow the reported line against the exact deployed source. These diagnostics require a fresh attempt after deployment; they cannot reconstruct the command that failed before instrumentation existed. A successful retry still needs HTTPS, sign-in and member-flow acceptance.
